# NixOS fleet

One `master` branch configures all three devices. Select the host explicitly;
there are no device branches.

| Device | Flake target | Platform | Configuration |
| --- | --- | --- | --- |
| Hetzner server | `.#hetzner` | `x86_64-linux` | [`hosts/hetzner`](hosts/hetzner) |
| Raspberry Pi 5 | `.#nixpi` | `aarch64-linux` | [`hosts/nixpi`](hosts/nixpi) |
| Raspberry Pi Zero 2 W | `.#nixzero` | `aarch64-linux` | [`hosts/nixzero`](hosts/nixzero) |

## Rebuild a device

Run the matching command from this repository **on that device**:

```sh
sudo nixos-rebuild switch --flake .#hetzner
sudo nixos-rebuild switch --flake .#nixpi
sudo nixos-rebuild switch --flake .#nixzero
```

Each command builds and activates that device's configuration. Use `build`
instead of `switch` to build without activating. On macOS, evaluation works
locally; building Linux systems requires a Linux builder of the matching
architecture.

The Zero evaluates locally and sends builds to the Pi 5 over Tailscale. Its
builder SSH key must already be installed and nixpi must be reachable. See
[Zero setup](docs/NIXZERO_SETUP.md) for provisioning and SD image builds.

## Move an existing checkout to master

With a clean working tree, run on each checkout when ready:

```sh
git fetch origin --prune
git switch master
git pull --ff-only origin master
git branch --set-upstream-to=origin/master master
```

If the checkout has no local `master`, use
`git switch --track origin/master` for the second command. Updating Git does
not activate NixOS; run the appropriate rebuild separately when intended.

## Validate without deployment

```sh
bash scripts/check-hosts.sh
nix flake check --all-systems --no-build --no-write-lock-file
```

The script evaluates all three complete system derivations and the Zero SD
image derivation. It neither builds nor activates systems. Keep `flake.lock`
committed; update inputs deliberately rather than during repository cleanup.

## Layout

- `hosts/<name>/`: host configuration, hardware, networking, and web routes.
- `modules/`: shared users, system components, editors, and service modules.
- `home.nix`, `home/`: Home Manager configuration for Hetzner and nixpi.
- `scripts/`: validation and Zero image/Wi-Fi/boot helpers.
- `docs/`: [Pi 5 / Nextcloud](docs/RASPBERRY_PI_SETUP.md),
  [Zero 2 W](docs/NIXZERO_SETUP.md), [Tailscale](docs/TAILSCALE_SETUP.md),
  and [Fitness AI](docs/FITNESS_AI_SETUP.md) setup notes.

Hetzner keeps its original `24.11` state version, Pi 5 keeps `25.11`, and the
Zero keeps `26.05`. The Zero intentionally omits the larger servers' services.
Hetzner's disk and static network settings were recovered from the previous
`master` and matched against `91.99.204.136` over read-only SSH on 2026-09-12.
Its configured hostname is now `hetzner` (the running server still uses `nixos`
until a future activation).

Hetzner's OpenCode OAuth service reads its existing client ID, client secret,
and cookie secret files from `/etc/nixos/secrets/` at runtime. Keep those files on the host when
updating the checkout; cookie base64 normalization happens in a private runtime
directory. No replacement credentials are generated by this configuration.

Generated images live in ignored `artifacts/`. Keep Wi-Fi credentials and
host runtime environment files out of Git and the Nix store.
